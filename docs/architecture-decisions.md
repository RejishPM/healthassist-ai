# Architecture Decision Records

## ADR-001: Use PostgreSQL with pgvector

### Decision

Use PostgreSQL with pgvector for initial vector storage.

### Reason

- Relational metadata and vector search in one database
- Familiar SQL model
- Easy joins between documents, chunks, and vectors
- Suitable for the MVP
- Supports future metadata filtering

### Status

Accepted


## ADR-002: Separate chunks and embeddings

### Decision

Store document chunks and embeddings in separate tables.

### Reason

A chunk may eventually have vectors generated by different embedding providers or models.

This avoids coupling source content directly to a single embedding model.

### Tradeoff

Retrieval requires a join between embedding and chunk tables.

### Status

Accepted


## ADR-003: Abstract embedding provider

### Decision

Use an embedding abstraction rather than calling Ollama directly throughout the application.

### Providers

- Ollama for development
- Bedrock for future cloud environments

### Reason

Avoid vendor lock-in and allow environment-specific embedding providers.

### Status

Accepted


## ADR-004: Rename embedding foreign key

### Previous Name

ollama_embeddings.chunk_id

### New Name

ollama_embeddings.document_chunk_id

### Reason

The value references document_chunks.id, not document_chunks.chunk_id.

The old name was ambiguous.

The new name clearly communicates that the field is a foreign key to the document_chunks table.

### Status

Accepted
